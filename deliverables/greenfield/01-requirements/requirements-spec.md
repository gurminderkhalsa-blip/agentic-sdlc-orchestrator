# Requirements specification

Build a greenfield Spring Boot URL shortener HTTP service using Spring Data JPA and the configured H2 database. Clients can create links, follow short codes, retrieve link details and click counts, while operators receive operational logs and a persisted audit trail.

**Change type:** greenfield

## Functional requirements

- Expose an HTTP endpoint to create a link from a request containing a long URL.
- Accept only absolute URLs using the http or https scheme; reject malformed URLs and URLs using other schemes.
- Generate a cryptographically secure, unique short code of exactly 7 URL-safe characters and retry generation on a persistence collision.
- Allow duplicate submissions of the same original URL; each successful submission may receive a different code.
- Return the generated code, short URL, original URL and initial click count for a successful creation.
- Expose a redirect endpoint at /{code} that redirects known codes to their original URLs.
- Return HTTP 404 for an unknown code instead of redirecting.
- Increment a link's click count for every request that successfully resolves a known code for redirection.
- Expose an endpoint to retrieve a link's code, short URL, original URL and click count.
- Persist links using Spring Data JPA in the H2 database configured by the project.
- Persist audit events containing event time, action, short code when available, client IP, and outcome.
- Record audit events for successful link creation, rejected link creation, successful redirects and unknown-code requests.
- Log key operations and errors, including creation, validation rejection, redirect, unknown-code handling and unexpected failures.

## Non-functional requirements

- Use Spring Boot and Spring Data JPA conventions compatible with the existing Gradle project.
- Use the existing configured H2 database; persistence across application restarts is not required.
- Short-code generation must use a cryptographically secure random source and must not expose sequential or readily predictable codes.
- Short codes must be safe to place in a URL path without encoding.
- Click-count updates must be transactionally safe so concurrent redirects do not lose increments.
- Validation failures must return a machine-readable error response with a clear human-readable message.
- HTTP responses must use appropriate status codes: 201 for creation, 200 for details, 3xx for redirects, 400 for invalid creation requests, and 404 for unknown codes.
- Do not log credentials, secrets or other configuration-sensitive values.
- Audit writes and operational logging should include timestamps generated by the service and use a consistent action vocabulary.
- The service should preserve the original URL exactly as accepted, subject to normal request JSON parsing.

## Out of scope

- User accounts, authentication, authorization or per-user link ownership.
- Link expiration, deletion, editing or administrative management APIs.
- Custom aliases or client-selected short codes.
- Analytics beyond the aggregate click count and required audit events.
- Persistent storage across application restarts.
- Rate limiting, quotas, abuse detection and malware scanning.
- Support for schemes other than http and https.
- A web UI or HTML management console.
- Guaranteeing that every submitted URL is reachable or safe to visit.

## Open questions, answers and assumptions

| Question | Human answer | Assumption |
|---|---|---|
| What exact public API paths and JSON field names should be used for creation and details? |  | Use POST /api/links with JSON body {"url":"..."}, GET /api/links/{code} for details, and GET /{code} for redirects. Use response fields originalUrl, code, shortUrl and clickCount. |
| Should a successful redirect use 301, 302, 303 or 307? |  | Use HTTP 302 Found so each visit is handled by the service and counted without implying permanent caching. |
| What should happen when a URL is submitted more than once? |  | Create a separate link record and generate a new code; deduplication is not required. |
| What client IP should be recorded when the service is behind a proxy? |  | Record the servlet request remote address and do not trust forwarded headers unless explicitly configured later. |
| What audit code should be stored for a rejected creation when no code exists? |  | Store a null code and include the validation reason in the outcome field. |
| Should URL validation permit query strings, fragments, internationalized domains and non-default ports? |  | Permit any syntactically valid absolute HTTP(S) URL, including query, fragment and port components, subject to the standard URL parser; no network reachability check is performed. |
| What exact audit action and outcome vocabulary is required? |  | Use actions LINK_CREATED, CREATION_REJECTED, REDIRECTED and UNKNOWN_CODE, with outcomes such as SUCCESS, INVALID_URL, REDIRECTED and NOT_FOUND. |
