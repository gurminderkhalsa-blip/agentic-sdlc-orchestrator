## Security review findings

The change improves scheme validation, canonical self-origin checks, expiration, and per-instance creation throttling, but several reliability and abuse-resistance gaps remain. The most significant issues are unbounded in-memory rate-limiter state, unrestricted short-code probing, missing HTTP request-size limits, and a development-style localhost fallback for public URL construction.

| Severity | File | Issue | Recommendation | Disposition |
|---|---|---|---|---|
| MEDIUM | src/main/java/com/example/shortener/service/CreationRateLimiter.java | The per-IP window map grows without eviction. Every distinct remote address creates a permanent ConcurrentHashMap entry, so an attacker able to generate many distinct source addresses can exhaust heap memory even though each individual IP remains within the 30-per-minute limit. | Bound and expire limiter keys, for example with scheduled cleanup, an inactivity TTL, or a bounded cache. Preserve the explicitly accepted per-application-instance behavior while preventing unbounded key retention. | Non-blocking; recorded as a follow-up |
| MEDIUM | src/main/java/com/example/shortener/controller/RedirectController.java | Unauthenticated redirect requests have no rate limiting or abuse control. The response differs for valid and missing seven-character codes, providing an enumeration oracle. Although the 62^7 search space is large, automated probing remains possible and can expose links if codes are leaked or the code space is reduced. | Add read-side abuse controls such as per-client/IP throttling, response monitoring, and optionally a uniform failure strategy. ## Remaining risks

- The explicitly accepted per-application-instance limiter is not a distributed quota; a load-balanced deployment can exceed 30 aggregate requests per minute.
- Rate limiting by direct remote address can group many users behind NAT or a trusted proxy and intentionally ignores forwarding headers.
- Open external redirects and lack of malicious/private-network destination scanning remain accepted out of scope by the binding decision.
- Nullable expiresAt preserves legacy links as non-expiring, while schema rollout still requires the nullable column to exist before production deployment.
- Audit persistence failure can reduce operational completeness despite the failure log.

## Trade-offs

- The implementation prioritizes the required direct remote-address identity over forwarded-header convenience.
- Expiration is enforced at an exact Instant using an injectable clock rather than calendar dates.
- Audit failures retain the user-facing 429/410 response instead of replacing it with a database error, at the cost of requiring separate audit-failure monitoring.
